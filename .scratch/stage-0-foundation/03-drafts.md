# 03 的草案：core 怎麼存、怎麼算（設計兩次）

段二 2026-10-30。照 `codebase-design` 的「設計兩次」做三個差很多的草案，比完選 A。結論與定下來的形狀在 [ADR 0001](../../docs/adr/0001-events-as-source-numbers-at-read.md)；這份留著當比較的紀錄。
草案是段二自己做的，沒開 subagent（資料都已經讀進來了，開 subagent 要每個再讀一次）。

## 每個草案都要滿足的

- 一次動作一則事件，上面掛好幾個效果（README）；窩日記之後讀同一批事件。
- 錢的定義照 GLOSSARY：我用的看幫誰、我付的看誰出、往來帳、還款先抵最早、寶媽卡、待收、按月攤、視角。
- 每個數字都能依誰出、帳戶、要不要還、罐子、標籤、固定花費、分期拆開，拆開的加起來等於總數。
- 離線也能記（之後 APK 殼靠它）；兩個人都會記，誰記都可以、一筆只記一次。
- 隱私：幫自己付的對方看不到；跟兩個人有關的兩個人都看得到。
- `packages/core` 不碰 Firebase（依賴分類：純計算，in-process）。

## 草案 A：事件存原樣，讀的時候全部算

存的只有事件（照使用者記的樣子：誰出、幫誰、品項、不用還、待收…）和參考資料（人、帳戶、罐子、標籤）。
所有數字都在 core 裡從頭算。

```ts
const book = openBook(catalog, events);
book.total({ measure: "use", person: 寶, from: "2026-10-01", to: "2026-10-31", where: { jar: 冥想 } }); // 寶的冥想罐這個月
book.breakdown(sameQuery, "repay");      // 自己付的／要還的／被寵的，加起來等於上面那個數字
book.lines(sameQuery);                   // 點一下展開：是哪幾筆
book.debts({ channel: "othersCard", person: 寶 }); // 寶媽卡每一筆已還多少、還欠多少
validateEvent(event, catalog); participantsOf(event, catalog); splitEvenly(1000, 3);
```

藏在裡面的：整筆的預設套到品項、共付的分法與零頭、按月攤切成每月一份、還款先抵最早（往來帳還會被之後反方向的花費抵掉）、
對帳差額看順序、標籤合併、退款沖回原本那一項、直接給錢變成對方的收入、收件匣的不算、看不到的帳戶。

## 草案 B：存的時候展開成分錄

記一筆時 core 把事件展開成好幾行「分錄」（誰、哪個數字、多少、哪一天、罐子、標籤、誰出…），分錄跟事件一起存進 Firestore。
讀的時候只加總分錄，可以用 Firestore 的加總查詢（sum）不用讀全部。

```ts
const postings = postingsOf(event, catalog);   // 存事件時一起存
sum(postings, { measure: "use", person: 寶, month: "2026-10", jar: 冥想 });
```

卡住的地方：還款先抵最早、對帳差額看的是順序，補記一筆舊的、改一筆、刪一筆，之後所有分錄都要重算重寫；
加一個新的視角面向，要把存過的分錄全部重寫；每一份分錄也要帶「誰看得到」；Firestore 的加總查詢離線不能用。

## 草案 C：存事件時順便更新彙總

每人每月一份彙總文件（每個罐子的我用的、我付的、往來帳、每個帳戶的餘額），記一筆時同一批寫入加加減減。讀的時候只讀彙總。

```ts
const patch = applyEvent(event, catalog);   // 存的時候一起寫：{ "2026-10/寶": { "use.冥想": +3000, ... } }
const undo = revertEvent(oldEvent, catalog); // 改、刪的時候要剛好減回去
```

卡住的地方：視角只能看事先挑好的組合（罐子 × 標籤 × 誰出 × 要不要還會爆量）；改、刪一定要剛好減回去，錯了查不出來；
還款先抵最早、對帳差額沒辦法用加減做；步記「步幫寶付」要改到寶的彙總文件。

## 比較

| | A 存原樣、讀時算 | B 存時展開成分錄 | C 存時更新彙總 |
|---|---|---|---|
| 視角（任何數字依任何面向拆開，加起來等於總數） | 做得到：每一行都帶齊所有面向 | 只有存的時候想到的面向 | 只有事先挑好的組合 |
| 還款先抵最早、對帳差額（看順序） | 每次照順序從頭算，補記舊的也對 | 補記、改、刪都要重寫之後的分錄 | 做不到 |
| 規則改了（例如零頭算誰） | 改 core，所有數字自動對 | 存過的分錄全部重寫 | 彙總全部重算 |
| 離線、兩個人同時記 | 一個動作寫一份文件 | 事件＋好幾份分錄同一批寫 | 事件＋好幾份彙總；會改到對方的彙總 |
| 權限 | 每則事件一個參與者清單 | 每份分錄也要帶 | 每人一份，往來帳那份兩人共寫 |
| 窩日記 | 只讀事件 | 只讀事件 | 只讀事件 |
| 讀取量 | 要讀所有看得到的事件（ADR「後果」） | 少，但加總查詢離線不能用 | 最少 |
| 測試 | 事件進、數字出，純函式 | 分錄是純函式，加總要模擬器 | 要模擬儲存的狀態 |
| 深度（介面小、藏得多） | `openBook`＋四個方法，規則全藏在裡面 | `postingsOf`＋`sum`，但規則的結果凍在資料裡 | `apply`／`revert` 要剛好互逆，呼叫的人要知道什麼時候叫哪個 |

**選 A**：使用者最在意的三件事（視角、先抵最早、不灌水）只有從原始事件重算做得到；B、C 省下的是讀取量，那可以在儲存那一層解決（增量同步），不用把規則凍進資料裡。

## A 裡面再比一次：介面長什麼樣子

- **A-1 每個數字一個函式**：`myUse`、`myPaid`、`tabBalance`、`accountBalance`、`netWorth`、`jarBreakdown`… 每多一個問題（「問問題」頁有十幾題）就多一個函式，篩選、日期、視角的邏輯每個函式各寫一次。
- **A-2 一種查詢**（選這個）：數字的種類（measure）× 面向（dimension）× 篩選。`total`、`breakdown`、`lines` 三個方法回答所有「多少」的問題，`debts` 回答「哪一筆還欠多少」。
  新的問題通常只是新的查詢，不用改 core；新的面向加在 core 裡一個地方。
