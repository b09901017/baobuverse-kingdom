# E2E 太慢的時候

這支是從一個真的跑過整輪加速的專案改寫的（上一個專案 `baobao-wellness-clinic-scheduler`，2026-09-09：CI 全量 21.7 → 8 分 05 秒，日常驗收 21 分鐘 → 1～2 分鐘，一支測試沒刪、一個斷言沒放寬）。
那一輪的細節留在那個專案的 `.claude/skills/test-speed/` 與 `.scratch/e2e-speed/`；這裡只留換到別的專案也成立的部分。

文中的每一個數字都標了出處。**換一個專案，數字要重量**：拿來當「大概會落在哪」的參考，不要抄進新專案的文件。

## 三條先記住

1. **先量，不要猜。** 上一個專案推估過兩個數字（「無頭快一倍」「分片省 60%」），兩個都錯，而且都已經寫進文件才發現。沒量過的數字不寫進任何檔案。
2. **拿掉墊子會露出東西，那是收穫。** 拿掉一個固定 350ms 的等待之後八支紅了，七支的根因是一個從第一天就在的缺陷。紅了先問「它為什麼現在才紅」，不要急著把墊子加回去。
3. **新的判準不可以比舊的寬。** 固定等待換成「等狀態」時，新作法最快放行的時間不可以早於原本那個秒數；不然換到的是「比較快、比較容易錯」。

## 第一步：量

跑一次全量（或最常跑的那一組），用 Playwright 的 JSON 報表看每個檔幾秒：

```bash
node <這支 skill 的資料夾>/scripts/durations.mjs .artifacts/results.json          # 每個檔
node <這支 skill 的資料夾>/scripts/durations.mjs .artifacts/results.json --tests  # 最慢的 30 個測試
```

把時間分成三桶，先找最大的那一桶：

| 桶 | 怎麼算 | 上一個專案（2026-09-09） |
|---|---|---|
| 每個測試的固定成本 | 最短那個測試的秒數 × 測試數 | 3.5s × 193 ＝ 11 分鐘（一半） |
| 空等 | `grep -o "waitForTimeout([0-9]*)"` 加總 | 217 個呼叫 ＝ 216 秒 |
| 全部都跑 | 全量時間 − 這次改動相關的那幾支 | 21 分鐘 vs 1～2 分鐘 |

**本機的總時間不能拿來比前後。** 同一份程式在同一台筆電跑出過 16.5 和 21.3 分鐘（差 30%，上一個專案 2026-09-09）。要比就比單一檔的秒數，或丟到 CI 上比（同一種機器）。

## 第二步：照這個順序挑

順序是「省多少 ÷ 風險多大」，不是省下來的秒數。

| | 做什麼 | 上一個專案的實際值 | 風險 |
|---|---|---|---|
| ① 分級 | 日常只跑跟這次改動相關的那幾支 | 21 分 → 1～2 分 | 低 |
| ② 無頭 | 拿掉 headed 與 `slowMo` | 一個檔 66s → 18.6s | 零 |
| ③ CI 分片 | 全量丟給 CI，幾台機器各跑一份 | 21.7 分 → 8 分 05 秒（3 台） | 幾乎零 |
| ④ 拿掉空等 | 固定等待換成等狀態 | 一個檔 330s → 120s | 中，會露出真缺陷 |
| ⑤ 砍固定成本 | 登入只走一次、不要每個測試清空 | 登入只走一次：每測試 −1 秒、全量 −3.2 分 | 高 |
| ⑥ 同機平行 | 一台機器開多個 worker | 見下面「同一台機器開多個 worker」 | 看隔離做得怎樣 |

**①②③ 先做完再碰 ④⑤⑥。** 前三個不動共用的測試程式，壞掉最多就是 CI 紅。

### ① 分級：日常唯一有感的那一個

一天驗收五次、全量二十分鐘就是兩小時。對照表（改了哪些檔 → 跑哪些 spec）要**大聲地壞**：新增一支 spec 忘了登記要紅、路徑不存在要紅，**認不出來的檔一律退回全跑**。少列一條的代價要是「多跑幾支」，不可以是「那一支沒跑到而且看不出來」。

比較基準選「上一次全綠」而不是「主分支」：上一個專案量過，對主分支比的話一輪做到後段幾乎每次都全選（一輪收尾時 50～69／69 支，2026-10-16）。

### ③ 分片 ≠ workers

- `workers: N` ＝ 同一台機器 N 個瀏覽器，**預設共用一組模擬器／後端**，會搶資源、可能互洗資料。
- `--shard=i/N` ＝ N 台機器，各有自己的一整套。沒有東西共用。

分片是繞過問題，只在 CI 有用。**地板 ＝ 每台開機成本 ＋ 最大那一個檔**：分片切不開一個檔。上一個專案 CI 每台開機約 70 秒（setup 45＋模擬器 25，2026-10-16）。
三台差不多、最慢的超過 10 分鐘 → 加一台；最慢的是別人兩倍以上 → 加台沒用，去拆那個肥檔。

## 在哪裡跑

| 在哪 | 適合 | 上限從哪來 |
|---|---|---|
| 這台筆電 | 日常的「相關的那幾支」 | **最多 2～3 個 worker**（使用者說的：「本機也可以開 2、3 個 worker 跑沒關係」）。i5-1240P（12 核 16 緒）：閒置 3%、1 個無頭 Chromium 整機 25%、2 個 43%（上一個專案記憶，2026-10-02）。CPU 全滿一個多小時過熱斷電過兩次 |
| 雲端 VM | 想在本機以外跑全量、或多開 worker | e2-standard-4（4 vCPU，客廳 `vm/README.md`）。沒量過在上面跑 E2E 的時間，要用先量 |
| GitHub Actions | 全量 | 分片，見 ③。不佔她的電腦 |

在她的筆電上跑，**每一次都先講**：大約多久、會開幾個瀏覽器／模擬器、CPU 大約多少；超過十分鐘給選擇。跑完把模擬器、Java、瀏覽器程序關掉並確認（中斷之後 port 不會自己放掉）。不要用 `Start-Process`／`nohup` 讓工作脫離對話。

## 同一台機器開多個 worker

先決條件是**隔離**：每個測試開頭通常會清空資料庫，兩個 worker 共用一份就是互相洗掉。隔離有兩種，數字與做法在 [`references/parallel-emulators.md`](references/parallel-emulators.md)：

1. **同一組模擬器、每個 worker 一個命名空間**（Firebase：每個 worker 一個 `projectId`）。資料分開了，但 CPU 與那一個 Java 行程還是共用。上一個專案 3 個 worker：193 個測試紅 10 個，沒開（2026-09-09）。
2. **每個 worker 一整組模擬器**（不同 port）。連行程都分開。2026-10-29 在同一台筆電試 2 個 worker、10 個檔：78 個全過，6.3 → 3.5 分鐘，CPU 平均 29%（中間有一次斷網紅了 8 個，重跑全過）；3 個 worker 也全過、3.0 分鐘，CPU 平均 40%、最高 77%——比 2 個只再快半分鐘，每個測試開始變慢。全量沒量過。

不管哪一種，**CDN 還是共用的**：前端 SDK、字型每個測試從網路抓一次，斷網或被重置時整批紅，看起來像平行壞掉。紅了先看錯誤裡的網址。

動隔離之前，**先做一支會大聲的檢查**：問 app「你讀的是哪一個命名空間／哪一組」，對不上就丟例外。對不上的症狀是「畫面全空、沒有錯誤訊息」——跟「這位客戶本來就沒資料」長得一樣，沒有這支檢查就只能猜。

**不要用加 retries、調大「等畫面穩定」的次數讓平行變綠。** 那是拿墊子蓋住訊號。

## 第三步：固定等待換成等狀態

`waitForTimeout(N)` 兩邊都錯：順的時候白等，慢一拍的時候讀到還沒重畫的畫面，而兩種症狀都不指向那一行。

| 在等什麼 | 換成 |
|---|---|
| 點一下之後有一層推上來 | 等那一層裡一定會有的東西 visible |
| 存檔 | 等「儲存中」的提示離開（寫失敗要丟例外） |
| 一頁畫完 | 等佔位字消失，**而且**內容連續 N 次沒變 |
| 按鈕被按下 | `toHaveAttribute('aria-pressed', 'true')` |
| 摺疊打開 | `toHaveAttribute('open', '')` |
| 長按 | 按住直到選單出現再放手 |

**兩種不要換**：等的是真實時間本身（長按門檻、產品定義的逾時）；要證明某件事**沒有**發生——先找一件「該發生的事」等它結束再斷言，找不到就留著固定等待，那一行寫出理由。

用一張只准變短的豁免表管進度（例如一個掃原始碼的測試，列出還允許固定等待的檔），清完一個就刪那一列。

## 踩過的坑

見 [`references/pitfalls.md`](references/pitfalls.md)。動手前掃一遍，至少看標題。

## 什麼時候停

```
地板 ＝ 開機成本 ＋ 最大那一個檔
```

離地板還遠就繼續，接近了就停。**量出來不值得就關掉那個念頭，把數字寫下來**：上一個專案的「一個測試一個命名空間」量完只省 7 秒（全套 0.6%），代價是動最深的共用 fixture——關掉、數字寫進 issue。那是正確結果，不是沒做完。

分清楚在優化誰的時間：日常那一段（分級）是她一天碰五次的；全量是 CI 在跑的。①做完之後剩下的多半是在優化「按一下就丟給 CI」的東西，那時候該回去做功能了。

## 收尾要留下什麼

- 每一個決定的**實際數字**寫進專案的 issue（`.scratch/<slug>/`），不是只寫在 PR 裡：下一個對話讀那個檔要接得下去。
- 量了發現不值得的，也寫下數字再關掉。
- 新長出來的守衛（掃原始碼的測試）要能自己說出「該怎麼修」，不是只說「錯了」。
