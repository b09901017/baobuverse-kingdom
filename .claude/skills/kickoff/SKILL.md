# 開一輪大改動

這支 skill 的存在理由只有一個：**把「決策」和「幹活」拆開。**

一次跑到底會讓 context 越來越長，被自動摘要時最先被壓掉的是細節和使用者的原話。
對抗的辦法不是少講幾輪，是**把知識寫到 context 以外的地方**：`.scratch/<slug>/`。

流程是四段：**談 → 開 issue 與分段 → 一段一段做 → 審查與合併**。
第一段結束一定要停；第二段結束也停（把下一段的開場交給使用者），除非整輪小到當下就做得完。

`CLAUDE.md` 已經規定的東西（先讀哪些文件、驗證指令、issue 格式）這裡不再重寫。

---

## 第一段：先回答，不要動 code

**一行程式都不要改。** 這一段的產出是對話裡的答案。

1. **分出兩種需求。** 「這是 bug」跟「這條邏輯怪怪的」是兩種工作：
   - bug → 找到哪一行、修
   - 「邏輯怪怪的」→ 先翻 `docs/plan.md` 的「使用者的決定」和 `docs/adr/`，問「當初為什麼這樣決定」，
     可能的答案是「那個決定還成立，是畫面沒講清楚」
2. **回答使用者問的設計疑問，從紀錄找證據**（plan、ADR、commit 歷史），不要憑讀 code 推測當初的意圖。
   找不到就說找不到，編一個理由比說不知道糟得多。
3. **清查連動。** 把實際依賴要改的東西的模組全部列出來（`grep`、graphify 都用），
   一支一支說會怎麼受影響。`docs/agents/lessons.md` 的每一句自問掃一遍。
4. **提出策略與風險，包含「不改」這個選項。** 推翻既有決定要說清楚推翻哪一條。
   想到使用者沒講、但照使用者的用法一定會撞到的情境，提出來。
5. **停下來。** 用表格、白話，一題附一個建議（使用者可以只回「照建議」）。

### 第一段結束時要問的

- 要使用者拍板的幾題（每題附建議）
- 哪幾條必須一起出貨
- 策略同意嗎？不同意哪一段
- issue 要逐支看過，還是 subagent 過目後直接分段

## 第二段：開 issue、過目、分段，再停一次

取得共識之後才開檔案。格式見 `docs/agents/issue-tracker.md`。先 `git fetch`，從最新的 `origin/main` 開這一輪的分支。

- `.scratch/<slug>/spec.md`：這一輪的全貌、使用者的原話、談定的策略
- `.scratch/<slug>/issues/NN-<slug>.md`：一支一個可以獨立出貨的東西
- `.scratch/<slug>/HANDOFF.md`：分段、每一段的開場、進度、中途發現的事

每一支 issue 一定要有：

| 那一塊 | 放什麼 |
|---|---|
| 使用者要的 | **原話，逐字貼上，不要整理** |
| 為什麼會這樣 | 現在那一行在哪、為什麼長這樣、相關的決定 |
| 判準 | 怎麼知道做對了。寫成「這一行會不會讓 X 被算成 Y」的問句，不是「要能正常運作」 |

還要有 `Status:`（`todo` / `done`）、「動工前先讀」、依賴（`Blocked by: 04`）。

### 過目

使用者不逐支看的時候，開一個**唯讀**的 subagent 對著程式碼過目：檔名、函式、現在的行為描述對不對；
設計做不做得出來；漏掉的連動；判準能不能寫成測試；依賴與分段；公開 repo 不能有真名或帳號資料。
subagent 也會看錯，主控**自己再對一次最重的幾條**再改。

### 分段

**不要為了分段而分段。** 小到這個 session 做得完就直接做。要分的時候，照「下一段需不需要
繼承我剛想過但沒寫下來的東西」來切：需要的寫進 issue 或 HANDOFF，然後切。

| 這一段在做 | 建議 effort |
|---|---|
| 動資料模型、金流規則、跨模組資料形狀 | xhigh |
| 畫面、接線、互動 | high |
| 文件、部署、跑測試、開 PR | medium |
| `/matt-code-review` | xhigh，**單獨一段** |

**每一段的開場**寫進 `HANDOFF.md`，並把第一段實作的開場貼在回覆裡（程式碼區塊，使用者直接複製到新 session）。
開場要自己站得住，新 session 什麼都不記得：

- 這一輪在做什麼（一句）、分支名、上一段做到哪
- 先讀：`HANDOFF.md`、`spec.md`、這一段那幾支 issue、`docs/agents/lessons.md`
- 這一段做哪幾支、**不做**哪幾支
- 中途發現的問題先記進 HANDOFF 的「中途發現」，繼續做別的
- 做完要交：每支一個 commit、`Status: done`、驗證指令通過、更新 HANDOFF、列出中途發現、下一段的開場與 effort

然後**停下來**。

---

## 第三段：一段一段做

動工前先 `git fetch`；這一輪的分支落後 `main` 就 rebase，不要重做。

一支 issue 一個 commit，每一支都走完再開始下一支：

1. 紅燈：先寫一支重現得出來的失敗測試，跑過確認它真的紅
2. 修到綠
3. 跑驗證指令
4. commit，`Status:` 改成 `done`，在 issue 底下寫「做完時留下的」（實際做成什麼樣子）

一支一個 commit，是為了讓使用者可以在任何一支之後說「停，方向不對」，做完的不用回頭。

**中途發現的事不要當場岔出去修**，記進 HANDOFF（哪裡、什麼情境會錯、建議），一段結束時一次列出來問要不要修。

一段結束：更新 HANDOFF → 列中途發現 → 貼下一段的開場（附 effort）→ 停。

---

## 第四段：審查、PR、合併

1. **`/matt-code-review`** 單獨一段，審這一輪全部的改動；照建議修，沒改的寫理由進 HANDOFF
2. **手動測試清單**：條列使用者可以**照順序點**的路，而且自己真的走過一次。
   寫「首頁 → 點 + → 輸入 120 → 選錢包 → 存」，不是「修好了記帳」
3. 開 PR。推之前看一眼 commit 訊息與內文：公開 repo，不帶真名與帳號資料
4. CI 全綠、使用者同意之後合併

## 這一輪結束前

- 每一支 issue 都是 `done`，HANDOFF 寫了合進哪個 commit
- 推翻了使用者的決定，就回去更新 `docs/plan.md`，而且只寫使用者確認過的
- 踩到 `lessons.md` 沒寫過的新坑，照它的格式補一條
