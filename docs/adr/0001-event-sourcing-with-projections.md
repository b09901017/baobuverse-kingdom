# 一次動作寫一份事件，其他畫面都是投影

系統的核心理念是「記一個地方，其他地方跟著動」。做法是：使用者的一次動作只寫**一份**事件文件，
裡面帶一個效果陣列（金流、物品、追劇進度…）；帳戶餘額、日記、物品清單、追劇狀態
全部是由事件算出來的投影，由 Cloud Function 在事件寫入後更新，可以隨時砍掉重建。

## 為什麼不直接寫好幾張表

因為「同時寫三張表，中途失敗怎麼辦」是一個無底洞。單一文件寫入在 Firestore 本身就是原子的，
所以那個問題根本不會發生——事實來源只有一次寫入，成功或失敗都是乾淨的。投影失敗了重放就好，
資料不會壞。

## Consequences

- **投影是最終一致的。** 記完帳的瞬間餘額可能慢半拍，需要在 client 端樂觀計算補足體感。
- **必須做冪等。** Firestore 觸發是 at-least-once，同一則事件可能被投影兩次。用事件 id 去重，
  否則餘額會多扣。這是這個架構唯一真正的坑。
- **事件不可修改。** 使用者按「編輯」時，底層是追加一則修正事件，不是覆寫。刪除同理。
- **不預先算彙總。** 不建「每月分類統計」這類表。之後要餵 AI 分析時直接讀原始事件，
  預先彙總會讓資料被壓扁、換算法時回不去。
