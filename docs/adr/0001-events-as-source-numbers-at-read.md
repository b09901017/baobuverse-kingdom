# 事件存記下來的原樣，所有數字讀的時候才算

國庫的每一個數字（我用的、我付的、往來帳、餘額、淨資產、待收、寶媽卡還欠、對帳差額）都從事件算出來，**不另外存算好的總數或分錄**。
事件照使用者記的樣子存（誰出、幫誰、品項、不用還、待收…），`packages/core` 的 `openBook(catalog, events)` 每次照時間從頭算。
理由：使用者要每個數字都能從任何視角拆開、還款要先抵最早的、對帳差額看的是先後，這三件事只有「從原始事件重算」做得到；
代價是讀取量跟著事件數變多（見「後果」）。三個草案的比較在 `.scratch/stage-0-foundation/03-drafts.md`。

## 考慮過的

- **存的時候展開成分錄**（每筆存成好幾行「誰、哪個數字、多少」，讀的時候加總，可以用 Firestore 的加總查詢）：還款先抵最早、對帳差額看順序，補記一筆舊的就要重寫之後所有分錄；
  加一個視角面向要重寫全部；加總查詢離線不能用。
- **存的時候順便更新彙總**（每人每月一份，記一筆就加加減減）：視角只能看事先挑好的組合；改、刪要剛好減回去，錯了查不出來；先抵最早做不到；步記的會改到寶的彙總。
  之後覺得「讀全部太慢、存個彙總就好」時，先看這一條。

## 定下來、之後難改的形狀（型別在 `packages/core/src/model.ts`）

1. **一則事件一份文件**，事件裡有效果的清單；現在只有錢的效果（一筆），之後的物品、日記的一行各自一個 `type`。
   一筆有六種：支出、收入、轉帳、還款、對帳（存實際餘額，對帳差額是算出來的）、退款。一個動作有好幾筆（跨行轉帳＋手續費）就是同一則事件裡的好幾筆。
   退款是退款那天的一則新事件，指到原本那一項；原本那筆上的註記是畫面從退款算出來的，原本那則不用改（也改不了對方記的），退款那天的日記也查得到它。
2. **支出＝整筆＋品項**：整筆有誰出、帳戶、幫誰（預設）、不用還（預設）、整筆的標籤；每一項有名稱、金額、罐子、標籤，進階可以改幫誰、不用還、待收、按月攤、直接給錢。
   整筆的標籤**不複製**到品項，算的時候才套上，所以統計標籤不會重算。品項加起來要等於整筆。
3. **幫誰**是「某個人」或「共」（王國裡所有的人，沒寫比例就平分，比例存成 `{人, 份數}` 的清單）。品項只有一個罐子：共付的品項，每個人那一份算在自己的同一個罐子。
4. **金額是最小單位的整數**，幣別看帳戶（沒有帳戶的是台幣）；轉帳存出、入兩個金額（換匯）。
5. **人跟登入帳號分開**：事件裡記的都是人的 ID（步、寶），哪個登入帳號是哪個人存在另一份文件。寶還沒有帳號時，步記的「寶幫步付」照樣存得進去；寶有帳號後一對上就認得出來。
6. **用 ID 指，不存名字**：帳戶、罐子、標籤都是自己的資料。標籤合併是在被併的那個標籤上記「併進哪一個」，舊的事件不用改（也改不了對方記的）。
   退款指到原本那一項（事件＋一筆＋品項），還款手動指定時也指到品項。帳戶、罐子、標籤、固定花費不刪，用封存。
7. **日期存當地的日期字串**（`YYYY-MM-DD`，時間 `HH:mm` 另外存、可以沒有），日記就是查同一天；排先後看日期、時間、記下來的時間。
8. **誰看得到、誰能改**：每則事件的參與者從內容算（`participantsOf`：記的人、誰出、幫誰、動到誰的帳戶、還款兩邊），存進文件給規則用。
   只有記的人能改；看得到的其他人只能在自己那一格標有疑問。收件匣裡的事件（`pending`）任何數字都不算。

## Firestore 上怎麼放（05 照做）

所有資料放在一個「王國」底下：上線後要開測試網址時，免費方案不能開第二個資料庫，測試資料就放另一個王國。現在只有一個，ID 寫在 app 的設定裡。

| 路徑 | 放什麼 | 誰讀得到、誰能寫 |
|---|---|---|
| `kingdoms/{kingdomId}` | 王國本身 | 成員 |
| `kingdoms/{k}/members/{uid}` | `{ person }`：這個登入帳號是哪個人 | 本人讀；怎麼建是 05 的事 |
| `kingdoms/{k}/people/{personId}` | `Person` | 成員 |
| `kingdoms/{k}/accounts/{accountId}` | `Account` | 帳戶的主人（`owners`） |
| `kingdoms/{k}/jars/{jarId}`、`tags/{tagId}` | `Jar`、`Tag` | 成員（共付的事件兩邊都要認得罐子和標籤） |
| `kingdoms/{k}/recurring/{recurringId}` | `Recurring` | `owner` |
| `kingdoms/{k}/prefs/{personId}` | 自己的排序（帳戶卡片、罐子、標籤） | 本人 |
| `kingdoms/{k}/events/{eventId}` | 整則 `Event`（效果、品項都在裡面）＋下面四個欄位 | 讀：參與者；建、改：記的人；其他參與者只能改 `doubts.{自己}` |

事件文件比 `Event` 多四個欄位，是儲存那一層的（core 不知道）：
`participants`（`participantsOf` 算的，查詢用 `array-contains`）、`updatedAt`（伺服器時間）、`deleted`（刪除只做標記、留著）、`v`（形狀的版本，現在是 1）。

- 讀自己的事件：`events` where `participants array-contains 我`；日記再加 `date ==` 那一天（要一個複合索引）。
- 「寶幫共付、步記的」：參與者是步和寶，兩個人都讀得到，只有步能改。「步幫步付」：參與者只有步，寶讀不到。
- 寶還沒有成員文件時，參與者裡有寶的事件照樣存得進去（規則只要求記的人在參與者裡）。

## 後果

- **讀取量會跟著事件數長**。免費方案每天 5 萬次讀取；監聽斷線超過 30 分鐘再連上，會當成新的查詢、看得到的事件全部重算一次讀取。
  估計一年三千則左右，一天打開十次，一年後就接近上限。所以文件從第一天就有 `updatedAt` 和刪除標記：
  05 先用一般的監聽就好，讀取量到額度一半前（最晚正式上線前）換成「只讀 `updatedAt` 比上次新的、其他從本機快取讀」，資料不用改。
- **規則改了，過去的數字跟著變**。這是要的（修一次，全部對），但上線後改規則要記得：以前月份的數字也會變。
- core 要能處理**看不到的帳戶**：寶的帳本裡沒有步的帳戶，步付的共同花費指著步的帳戶，算寶的數字時不能當成錯。
- 窩日記只要讀 `events`，不用讀國庫特有的集合；它的效果加在同一則事件上。
