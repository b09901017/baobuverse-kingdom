## 完全不依賴版面的部分

不管最後選哪種畫風、哪種版面，這些都要做，而且長得一模一樣。
**大約佔總工作量的六到七成。**

| 工作 | 份量 | 風險 |
|---|---|---|
| 新 database + Security Rules | 中 | **高** —— 隱私規則複雜（私人／共享／跨人的 0 元紀錄），寫錯很危險 |
| Auth（沿用 `baobu-app`） | 小 | 低，`member_roles` 直接讀 |
| 事件寫入 API（`core`） | 中 | 中 |
| **投影引擎 + 冪等** | 中 | **最高** —— 這是心臟，做錯全部都錯 |
| 帳戶模型 + 分錄判定 | 中 | 低，規則已想清楚 |
| 餘額投影 | 小 | 中（要處理離線時的樂觀計算） |
| 對帳機制 | 小 | 低，就是一種特殊事件 |
| 國王日記鏡像 Function | 中 | 中 —— 跨 database，不能寫壞舊的 |
| 洗錢判定 + 雙邊事件 | 小 | 中 |
| 簡訊解析（AI 學模板，見 spec §5.1） | 中 | 中 |
| 固定支出排程 Function | 小 | 低 |
| 匯出 JSON | 小 | 低 |
| 離線快取 | 極小 | 低，幾乎是一行設定 |
| 測試環境（emulator + 測試 db） | 小 | 低 |

## 三個最貴的東西

### 1. 簡訊自動記帳 —— 已因「AI 學模板」而降價

原本估「最貴、永遠做不完」，是假設要為每家銀行手寫規則。
改用 spec §5.1 的做法（AI 判斷一次 → 存模板 → 之後套模板）之後降到**中等**，
而且銀行改版時系統會自己學回來。

**這是初版評估中改變最大的一項。**

### 2. 可切換畫風 —— 成本從第一行就開始付

只做 token 切換的話成本低。但要守紀律：`ui` 內不得寫死顏色、資料與畫面分離。
整份 UI 切換刻意排到最後（spec §7.7）。

### 3. 窩日記整個 app

七個模組。與國庫共用 `core`，所以第二個 app 比第一個便宜很多，
但仍是七個模組的畫面。

## 「一個月內能自己用」的最小切法

核心迴圈只有一句話：**記一筆 → 看到餘額。**

**留下**

- 新 database + 最簡 rules（先只做 `ownerId` 隔離，共享之後再加）
- 事件寫入
- 餘額投影 + 冪等
- 帳戶設定
- 一頁記一筆
- 一頁帳戶餘額

**砍掉**

- 簡訊自動記帳
- 國王日記鏡像
- 理財頁與 AI
- 收件匣（沒有草稿來源就不需要）
- 沉浸場景（先用純色）
- 整個窩日記

**為什麼這樣砍**：留下來的全是**之後絕對不會重寫**的東西——事件模型、投影、冪等、
分錄邏輯。砍掉的全是**可以獨立加上去**的東西，因為架構已經留好位置。

## 這對「先決定版面還是先寫」的影響

**目前糾結的版面問題，幾乎不影響 MVP。**

MVP 只有兩頁——記一筆、看餘額。這兩頁沒什麼好糾結的，記帳 app 都長差不多。
真正在糾結的是主畫面的沉浸感與理財頁長相，那些**都在 MVP 之外**。

所以存在第三條路：**先做 MVP，用真實資料自己用兩週，再回來決定主畫面。**
用過之後會知道自己每天真正在看什麼，那比看設計稿準得多。

這條路不是唯一解。如果享受設計探索的過程，先做視覺探索完全合理——
這是自己要用的東西，開心比效率重要。
