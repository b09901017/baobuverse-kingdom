## 1. 系統概觀

一個 monorepo、一個 Firebase 專案、**兩個獨立的 Android APK**。

| APK | 名稱 | 節奏 | 內容 |
|---|---|---|---|
| `baobu-treasury` | 國庫 | 快進快出 | 記帳、收件匣、帳戶、理財分析 |
| `baobu-nest-diary` | 窩日記 | 慢慢逛 | 追劇、家務、物品、靈感、優惠券、固定帳單、日記 |

monorepo 分四個 package：

- **`core`** — 事件寫入、Firebase、型別、帳戶與分錄邏輯。兩個 app 的共同地基。
- **`ui`** — 設計系統：導覽、字級階梯、間距節奏、動畫曲線、觸覺回饋、共用元件。
- **`treasury`** / **`nest`** — 各自的畫面與各自世界的主色、關鍵視覺、標誌性互動。

技術棧：React + Vite + TypeScript + Tailwind + motion，Capacitor 打包，
Firebase Auth / Firestore / Cloud Functions（Blaze），pnpm workspaces。

## 2. 資料模型

### 2.1 事件

使用者的一次動作 = **一份**事件文件。這是系統唯一的事實來源，append-only。

```
events/{eventId}
  ownerId       誰的事件
  visibility    private | shared
  type          事件種類
  occurredAt    發生時間 —— 日記按這個排序
  recordedAt    記錄時間 —— 用來看記帳頻率
  effects[]     這件事造成的影響（可多個）
  note          自由文字備註
  photos[]      照片
  sourceRef     來源（簡訊 / 固定支出 / 國王日記鏡像），手動輸入則無
```

**效果**種類：

| kind | 意義 | 主要欄位 |
|---|---|---|
| `posting` | 金流 | `from`, `to`, `amount` |
| `item` | 物品 | `itemId`, `action`（取得／保養） |
| `progress` | 追劇進度 | `showId`, `season`, `episode` |
| `chore` | 家務 | `choreId`, `doneBy` |

買一台空氣清淨機 3000 = **一則**事件，帶 `posting` 和 `item` 兩個效果。

### 2.2 投影

以下全部由 Cloud Function 監聽事件寫入後更新，**可以砍掉重建**，不得直接寫入：

帳戶餘額、追劇進度與狀態、物品清單、家務最後執行時間、欠款淨額、日記。

**日記沒有自己的 collection**。日記 = 查詢某天的事件（`occurredAt` 落在當天，
且 `ownerId` 是我或 `visibility` 是共享）。

### 2.3 修改與刪除

事件不可修改。畫面上照常提供「編輯」與「刪除」，底層是**追加一則修正事件 / 作廢事件**。
使用者感覺不到差別。修改歷史保留但預設不顯示。

### 2.4 冪等

Firestore 觸發是 at-least-once。所有投影必須以事件 id 去重，否則餘額會重複計算。

## 3. 金流規則

### 3.1 分錄

每筆金流都有出方與入方。**「支出」不是一種類型，是入方為外部節點的查詢結果。**

| 動作 | 出方 | 入方 | 是支出嗎 |
|---|---|---|---|
| 加值悠遊卡 | `acc:錢包` | `acc:悠遊卡` | 否 |
| 悠遊卡搭捷運 | `acc:悠遊卡` | `ext:捷運` | **是** |
| 刷卡買東西 | `liab:國泰卡` | `ext:商家` | **是**，且負債增加 |
| 還卡費 | `acc:國泰` | `liab:國泰卡` | 否，負債減少 |
| 領現金 | `acc:郵局` | `acc:錢包` | 否 |

使用者**不需要選「這是支出還是轉帳」**。選了入方是誰，答案就決定了。

### 3.2 標籤

畫面上是一排標籤，使用者照常點。系統內部拆成兩欄：

- **帳戶標籤**（錢包現金、郵局、國泰、悠遊卡、某張卡）→ 歸到「從哪出」，**固定清單**
- **分類標籤**（吃吃、訂閱、交通、寵寶寶）→ 留在標籤，**固定清單但可自行新增**

每筆帳一定要有一個帳戶標籤。**沒選就用預設帳戶（錢包現金）**，不卡住記帳流程。

### 3.3 對帳

現金與悠遊卡這類系統看不到的帳戶一定會對不上。提供「對帳」動作：
使用者宣告實際餘額，系統補上差額，分類為**「說不清楚」**。

**刻意不追究漏記了什麼。** 「說不清楚」的累計金額本身就是有用的資訊。

初始餘額也走同一個機制，所以第一次設定填錯不用怕。

### 3.4 帳戶管理

第一次開 app 有設定流程：建立帳戶、填目前餘額。信用卡另填**結帳日與繳款日**。

之後隨時可新增與修改：

- 改名字、顏色 → 直接改
- **改餘額 → 走對帳機制**，不是覆寫
- **刪除 → 只能封存**，不能真刪（過去的事件指向它）

### 3.5 理財分析（獨立頁面）

記帳是主功能；以下放在**另一個頁面**（介面細節見 §7.6），不干擾記帳流程：

- 各帳戶餘額一覽
- 卡債總額、本月應繳（由結帳日區間內的刷卡總額算出）
- **可用餘額** = 資產總額 − 卡債 − 本月尚未發生的固定支出

## 4. 國王日記整合

### 4.1 方向

**單向：國王日記 → 新系統。** Cloud Function 監聽舊 database 的
`couples/{coupleId}/notebooks/{notebookId}/transactions/{txId}`，鏡像成新 database 的事件。
以來源交易 id 去重。新系統**永遠不回寫**。

角色對照直接讀 `couples/{coupleId}.member_roles`（`{ uid: 'baobao' | 'bubu' }`）。
Auth 共用，**不需要重新配對**。

### 4.2 誰會收到

| payer → beneficiary | 寶這邊 | 步這邊 |
|---|---|---|
| 寶 → 寶（自己幫自己） | ✓ | — |
| 步 → 步（自己幫自己） | — | ✓ |
| 寶 → 步（幫對方） | ✓ 實際金額 | ✓ 0 元 + 備註 |
| 步 → 寶（幫對方） | ✓ 0 元 + 備註 | ✓ 實際金額 |
| 寶 → 共 / 步 → 共 | ✓ | ✓ |

對方那筆的擁有者是**對方**，內容只有品項、誰出的、多少。
**不含出錢人的帳戶與其他標籤。** 不能刪除，也不隱藏。

### 4.3 洗錢

寶步之間直接給錢（還款、代墊回沖、單純給錢），記在國王日記為一般交易 + 「洗錢」標籤。
新系統看到這個標籤，就把它從支出改判成**兩人帳戶之間的轉帳**。

雙方各自在收件匣裡補自己的帳戶（誰的錢包 +250、誰的錢包 −250）。

保留「算不算欠款」欄位，預設算；目前不做 UI。

## 5. 收件匣

**一個收件匣，兩種狀態：**

| 狀態 | 來源 | 計入餘額？ | 使用者要做什麼 |
|---|---|---|---|
| **待確認** | 銀行通知、固定支出到期 | **否** | 按確認才成為事件 |
| **待補完** | 國王日記鏡像 | **是**（先用預設帳戶） | 補帳戶與標籤 |

首頁常駐「N 筆待確認」。**不自動標記過期。**

### 5.1 銀行通知

MacroDroid 監聽 → POST 到 Cloud Function → 解析 → 寫入收件匣。

**只吃網銀 app、LINE Pay 這類金流通知，一般訊息不理。** 過濾在 MacroDroid 端做。

#### 解析方式：AI 判斷一次，之後套模板

**不預先為每家銀行手寫規則**——那是永遠做不完的工作。改成讓系統自己學：

1. 收到通知 → 先比對已知**模板**（把金額、商家、日期挖空之後剩下的文字骨架）
2. **對得上** → 直接套用，不呼叫 AI
3. **對不上** → 呼叫 AI 解析出金額／商家／卡別，**同時存下這封的骨架成為新模板**
4. 之後同格式的通知走第 2 步

因此 AI 只在遇到沒見過的格式時才動，用量與費用極低。
銀行改版導致骨架失效時會自動掉回第 3 步，**系統自己學回來**。

**這個 AI 跑在 Cloud Function（伺服器端）**，與理財頁的 AI 對話框（§7.6）
是兩件不同的事，可分開實作。伺服器端的好處是金鑰不落在手機上。

> ⚠️ AI 會解析錯，而且**錯得很有說服力**（例如把通知裡的「餘額」讀成消費金額）。
> 因此解析結果**一律進「待確認」**，永不自動記帳——與 §5 的既有決定一致。

AI 也讀不懂的照樣進收件匣，標為**「看不懂」**，讓使用者手動填。
**永遠保留通知原文**——模板與 AI 提示之後會改進，原文留著才能重新解析舊資料。

### 5.2 固定支出

到期日產生**草稿**進同一個收件匣，不自動記帳（電費每期金額不同，自動記一定錯）。
固定金額的訂閱按一下確認即可。

## 6. 窩日記各模組

### 6.1 追劇

進度以「追到哪裡」記錄（季 + 集），**不是一集一筆**。一天看五集 = 一筆事件。

狀態：**願望清單 / 正在追 / 等待續集 / 已看完 / 棄追**。

- 填了總集數 → 狀態自動推導
- **沒填 → 停在「正在追」**，「等待續集」與「已看完」手動標
- **棄追**永遠是手動宣告，且是追加事件不是改狀態（所以「常在第幾集棄劇」查得出來）

**不強制填總集數。** TMDB 之後再接。

每部劇有**「一起看 / 自己看」**標記，**預設一起看**：一份進度、兩人共用、誰更新都行。
「自己看」則各自記錄且對方看不到。

### 6.2 家務

固定清單，預設給一組常見的（洗碗、倒垃圾、洗衣服、拖地、換床單、洗冷氣），可自行增刪。

**兩種類型：**

- **日常型**（洗碗、倒垃圾）→ 關心誰做得多
- **週期型**（洗冷氣、換床單）→ 關心距離上次幾天

**不做排班表，不做待辦清單。** 待辦會變成壓力與吵架的來源；點一下就好的東西才會持續用。
「誰做比較多」的統計**不放首頁**。

### 6.3 物品

兩種事件：**取得**與**保養／更換**。

- 「用了多久」= 今天 − 取得日
- 「上次洗冷氣」= 該物品最後一筆保養事件
- 可設週期，但顯示為「距離上次 187 天」，**不做紅色未完成提醒**

從國庫進入的流程：記帳畫面常駐一個「這是個東西」按鈕，**使用者自己點，系統不自動判斷**。
點過幾次類似的之後，遇到相似項目**把按鈕變亮但不打斷**。

按下去**只多問一件事：名字**（預設帶備註文字）。分類、保養週期、照片之後在窩日記補。

> 「上次大爆買是什麼時候」**不是物品**，是記帳的查詢（單日支出超過某金額）。

### 6.4 靈感

唯一重點是**快**。一個輸入框，打完就存，不選分類、不填標題。之後想整理再回頭加標籤。

### 6.5 優惠券

拍照 + 到期日 + 在哪用。到期前提醒——**這裡可以用紅字**，因為過期是真的損失。

### 6.6 固定帳單

記錄本身走 §5.2。另提供**同一項目的歷史金額**查詢（這次電費比上次多嗎、夏天是不是特別高）。

### 6.7 日記

沒有 diary collection。日記 = 查詢當天事件。**各自一本，共同的事兩邊都會出現。**

## 7. 國庫的介面與互動

### 7.1 分層原則

> **待確認**：主畫面究竟是「沉浸場景」「AI 總結卡」還是別的，尚未定案。
> 下面的「成長指標」一段只在**確定要做會成長的東西**時才成立；
> 若最後沒有獎勵層，整段作廢。

**獎勵層常駐在背景，輸入層蓋在上面。** 主畫面是一個持續存在的沉浸場景，
不是交易列表；記帳是從底部滑出的面板。兩層互不干擾——這是「記帳城市」真正的結構，
也是為什麼它的記帳很快卻又讓人想打開。

> **成長指標必須是記帳行為，不是消費金額。** 連續記帳天數、記錄筆數、收件匣清空率。
> 若場景隨花費金額成長，這個 app 就變成在獎勵消費，與「掌握金流」的目的正好相反。

### 7.2 主畫面

- 沉浸場景常駐（見 §10 未定：實作方式）
- 上方：日期 + 當日總額，**左右滑切換日期**
- 底部固定三區：左下統計入口、中央「+ 新紀錄」、右下選單（帶未處理數字）
- 「N 筆待確認」的數字出現在右下選單上

### 7.3 記一筆

點「+ 新紀錄」→ 面板**由下往上滑出，覆蓋約 80%，不全屏**——背景場景仍露出一部分，
維持「還在那個世界裡」的感覺。

面板內容：金額、帳戶標籤、分類標籤、備註、照片，以及「這是個東西」與「寶步洗錢」兩個次要按鈕。

**硬性要求：常見情境三秒內完成，單手可操作。** 任何讓輸入變慢的裝飾都要砍掉——
獎勵發生在記完之後，不在記的當下。

### 7.4 記錄列與時間粒度

圓形分類 icon + 名稱 + 金額。當日總額置於日期列。

> **暫定，未定案**：粒度切換器（日／週／月）。切到「週」時左右滑就是上週、上上週；
> 切到「日」就是昨天、前天。
>
> 不需要新的資料結構——事件都在，按天或按週分組只是查詢方式不同，成本很低。
> 符合 ADR-0006：這是**呈現事實**（「上週吃吃 2,140」），不是推論規律。

### 7.5 帳戶頁

各帳戶餘額；信用卡顯示欠款。**另列出最近幾筆帳戶之間的金流**——
這正是「寶步洗錢」的可視化，回答「錢最近在我的帳戶之間怎麼跑」。

### 7.6 理財頁

留白為主，不塞滿圖表。

- **AI 對話框**：直接問。主要用途是**總結**——上個月、上禮拜、這幾天的花費模式。
- **可選的視覺化**：使用者自己挑要看哪幾張，不預設塞一堆。
- 本月固定支出、卡債、應繳金額、可用餘額。

> AI 只做**總結事實**，不做規律推論（ADR-0006）。餵給模型的提示必須明確要求
> 「描述資料，不要推測規律」，否則它會在小樣本上編出你會相信的假模式——
> 那正是我們決定不自己寫演算法的原因。

### 7.7 畫風切換與畫面架構

分兩層，**現在只做第一層**：

| 層級 | 現在做嗎 | 成本 |
|---|---|---|
| **token 切換**（配色、圓角、字體、陰影、動效強度） | ✅ 做 | 一次做好，之後免費 |
| **整份 UI 切換**（版面也不一樣） | ⏸ 留到最後 | 每加一個功能都要做 N 次，是**持續**成本 |

只做 token 切換，視覺差異已經足以像兩個不同的 app。

**現在就要守的兩條紀律：**

1. `ui` package 內**不得出現寫死的顏色**，畫面只引用 token
2. **資料邏輯與畫面分離**——資料怎麼算是一層，怎麼畫是另一層

守住這兩條，第二套 UI 就是**所有功能完成之後可以獨立加上去的一個項目**，
資料層一行都不用改。沒守住的話，之後再想加會痛到可能放棄。
紀律本身不費力，只是要記得。

## 8. 隱私與權限

同一個 database，靠 Security Rules 隔離。資料帶 `ownerId` + `visibility`，**預設 private**。

**共享的有**：分帳、家務、共同支出、標記為「一起看」的劇。

**私人的有**：個人記帳、個人日記、靈感、自己看的劇。

彼此看不到對方的記帳內容。跨線的只有 §4.2 那張表列出的情況，且內容經過裁剪。

## 9. 技術與環境

### 9.1 Firebase

共用專案 `baobu-app`，但**新開一個具名 Firestore database**（見 ADR-0002）。
國王日記的預設 database 與其規則檔案完全不動。

### 9.2 測試環境

- **開發**：Firebase Emulator，資料隨時清空，不碰雲端
- **真機測試**：專案裡的第三個 database，靠 build 設定切換
- **不使用 `isTest` 標記混在正式資料裡**——永遠刪不乾淨，且每個查詢都要記得過濾

### 9.3 離線

開啟 Firestore 離線快取。沒網路時照常記帳，連線後同步。
**餘額會慢半拍**（投影要連線才算），client 端先樂觀計算，以伺服器為準。

### 9.4 通知

**手機本地通知，不做伺服器推播。** 優惠券到期與固定支出到期的時間都能事先算出來，
不需要 FCM。日後若要即時通知（「寶做了家務」）再加。

### 9.5 資料匯出與 AI

提供區間匯出（JSON），供使用者自行貼給 AI 分析。

理財頁的 AI 對話框（§7.6）是**目標**，但實作順序在後：先做匯出與可選視覺化，
AI 對話框之後接上。接上時需要處理 API 金鑰與費用。

---

## 10. 明確不做的事

| 不做 | 理由 |
|---|---|
| 找規律的演算法、星象關聯 | 樣本數不足會產生假訊號，且會自我實現（ADR-0006） |
| 預先算好的統計彙總表 | 資料被壓扁，之後換算法回不去 |
| 國王日記的 `settlement` 型別 | 一般交易就能正確算出還款（ADR-0004） |
| 回寫國王日記 | 雙向同步的衝突無解（ADR-0003） |
| 家務排班表 / 待辦清單 | 會變成壓力與吵架來源 |
| 自動判斷是不是居家用品 | 判斷錯就變煩人彈窗，然後整個功能會被無視 |
| 全自動簡訊記帳 | 重複、預授權、取消會讓餘額飄掉，然後失去信任 |
| 草稿自動過期 | 使用者明確要求保留 |
